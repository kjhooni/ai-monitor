========================================
1. AI 활용 개요 (필수)
========================================

■ 활용 AI 모델/도구
- Anthropic Claude (claude-sonnet-4-6) — 서버 장애 상황 분석 및 자동조치 판단에 활용

■ 활용 목적
기존에는 관제팀이 모니터링 알람을 수신하고, 담당자에게 직접 연락하거나
야간/주말 당직 근무 중 단순 장애를 처리하는 방식으로 운영되었습니다.
이 과정에서 발생하는 대응 지연, 반복적인 단순 업무 부하, 담당자 개인 판단 의존 문제를
해소하기 위해 Claude AI를 활용한 자동 장애 분석 및 대응 시스템을 구축하였습니다.

■ 전체 흐름

[수집]
Prometheus + node_exporter
각 서버의 CPU / 메모리 / 디스크 / SWAP 메트릭 60초 주기 수집
        ↓
[임계값 초과 감지]
설정된 임계값 초과 시 SSH로 서버에 직접 접속하여
프로세스 현황, 디스크 사용 상세 등 진단 데이터 수집
        ↓
[AI 분석 - Claude]
수집된 메트릭 + 진단 데이터 + 과거 장애 이력을 Claude에 전달
→ 단순 임계값 초과인지 실제 장애인지 판단
→ 원인 프로세스 또는 원인 특정
→ 심각도(low / medium / high / critical) 결정
→ 권장 조치 및 자동 실행 가능한 bash 명령어 생성
        ↓
[알림]
Microsoft Teams Adaptive Card로 담당자에게 전송
→ 분석 결과 / 권장 조치 / TOP 프로세스 현황 포함
→ 담당자 멘션으로 즉시 인지 가능
        ↓
[조치 확인 및 실행]
Claude가 자동조치 가능하다고 판단한 경우
→ Teams 카드 내 "자동조치 실행" 버튼 제공
→ 담당자가 확인 페이지에서 명령어 설명 검토 후 실행 승인
→ SSH를 통해 대상 서버에 명령어 자동 실행
→ 실행 결과(stdout) 포함하여 Teams로 결과 통보


========================================
2. AI 활용 방식 및 차별성 (필수)
========================================

■ 핵심 프롬프트 구조
Claude에게 단순히 "디스크가 90%입니다"를 전달하는 것이 아니라,
아래 세 가지 컨텍스트를 함께 제공하여 전문가 수준의 판단을 유도합니다.

  1) 실시간 메트릭: 현재 수치 및 임계값
  2) 서버 진단 데이터: SSH로 수집한 ps, free, df 등 실제 서버 상태
  3) 과거 장애 이력: 동일 노드/메트릭의 최근 10건 발생 패턴

Claude에게 부여한 역할과 판단 기준은 다음과 같습니다.

  - 진단 데이터가 있으면 반드시 원인 프로세스/원인을 특정하여 분석
  - 과거 같은 시간대에 반복된 패턴이면 "실제 장애 아님"으로 판단 가능
  - 지속 시간이 짧고 자동 회복된 이력이 있으면 심각도를 낮게 조정
  - 원인이 명확하고 조치가 안전하다고 판단될 때만 자동 실행 명령어 생성
  - 원인 불명확하거나 운영 프로세스 여부 불확실하면 자동조치 생성하지 않음

응답은 JSON 구조로 강제하여 시스템이 결과를 그대로 처리할 수 있도록 설계하였습니다.
(is_real_incident / severity / analysis / recommended_action / auto_remediate / remediate_command)

■ 기존 방식 대비 차별화 포인트

  [기존 방식]
  - 모니터링 툴이 임계값 초과 시 무조건 알람 발송
  - 관제팀이 알람 확인 → 담당자에게 전화/메시지로 통보
  - 담당자가 직접 서버 접속하여 원인 파악 및 조치

  [AI 도입 후]
  ① 노이즈 필터링: 일시적 스파이크나 반복 패턴은 Claude가 "실제 장애 아님"으로 판단,
     불필요한 알람 차단 → 관제팀 및 담당자의 알람 피로도 감소

  ② 원인 즉시 특정: 알람 수신 시점에 이미 "어떤 프로세스가 원인인지,
     어떤 조치를 취해야 하는지"가 분석 결과에 포함 → 담당자가 서버 직접 접속 없이 파악 가능

  ③ 자동조치 실행: 단순하고 안전한 조치(로그 정리, 캐시 해제, 스왑 초기화 등)는
     담당자 승인 한 번으로 자동 실행 → 야간/주말 당직 업무 부담 대폭 감소

  ④ 조치 결과 피드백: 자동조치 후 실제 실행 결과(stdout)를 Teams로 재통보,
     효과가 없었던 경우도 즉시 인지 가능


========================================
3. AI 도입 효과 및 확장성 (필수)
========================================

■ 도입 후 개선 효과

  ① 대응 속도: 장애 감지 → 담당자 알림까지 기존 수 분(관제팀 확인 후 연락) → 60초 이내 자동 통보

  ② 당직 업무 감소: 단순 반복 장애(디스크 정리, 캐시 해제, 스왑 초기화)는
     담당자가 Teams에서 버튼 클릭만으로 처리 → 서버 직접 접속 불필요

  ③ 알람 품질 향상: 단순 임계값 알람 대신 원인과 조치방안이 포함된 분석 결과 제공
     → 담당자 판단 시간 단축 및 오대응 리스크 감소

  ④ 관제 인력 의존도 감소: 야간/주말 단순 장애 처리를 위한 관제 상시 운영 부담 경감,
     관제팀은 복잡한 장애 대응에 집중 가능

■ 타 부서 및 유사 업무 확장 방안

  ① 고객사 확장: config.yaml에 노드와 담당자 정보만 추가하면
     MSP에서 관리하는 모든 고객사 서버에 동일하게 적용 가능

  ② 모니터링 범위 확장: 현재 서버 리소스(CPU/메모리/디스크) 외에
     - 웹서비스 URL 헬스체크 (블랙박스 exporter)
     - DB 응답 시간 / 쿼리 지연
     - 네트워크 장비 상태 (SNMP exporter)
     등으로 수집 범위를 넓히면 인프라 전반으로 커버리지 확대 가능

  ③ 에스컬레이션 자동화: 담당자 미응답 시 N분 후 팀장/2차 담당자에게 자동 재알림,
     당직 스케줄 연동으로 시간대별 담당자 자동 라우팅

  ④ 정기 리포트: 일/주/월 단위로 장애 건수, 자동조치 성공률, 노드별 이상 빈도 등을
     Teams로 자동 발송하여 운영 현황 가시성 확보

  ⑤ 타 업종 적용: 서버 모니터링 외에도 동일한 구조(수집 → AI 판단 → 알림 → 자동조치)를
     네트워크 이상탐지, 보안 이벤트 1차 분류, 클라우드 비용 이상 감지 등에 적용 가능
